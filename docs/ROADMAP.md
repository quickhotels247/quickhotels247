# QuickHotels24/7 roadmap

We build one step per chat. At the start of each chat, read this file and the product spec ([QuickHotel247_UI_and_Product_Documentation.docx](QuickHotel247_UI_and_Product_Documentation.docx)). At the end, tick the step off and add any notes for the next one.

Target stack: **Nx monorepo, Next.js (App Router) + React 19 + MUI, NestJS, Prisma, PostgreSQL, Redis/BullMQ.**

Rules that keep the later move a simple `pg_dump`/`pg_restore` and a `DATABASE_URL` change:
  - The Neon project `quickhotels247` is in **AWS Asia Pacific 1 (Singapore)**, the closest region Neon offers to India. While on Neon, host the backend in Singapore too. When we move to RDS, put RDS and the backend in **Mumbai (`ap-south-1`)**; `pg_dump`/`pg_restore` works across regions.
  - Use a PostgreSQL major version that RDS also offers, and match it on RDS.
  - Use Prisma with the standard Postgres driver, not Neon's serverless/HTTP driver.
  - Use Neon's pooled URL as `DATABASE_URL` for the app and the direct URL as `DIRECT_URL` (Prisma `directUrl`) for migrations.
  - Only use extensions RDS supports (`pgcrypto`, `uuid-ossp`, `pg_trgm`).
  - Run the backend as a long-running server, not as serverless functions.
  - Live TripJack rates and search sessions go in Redis, not Postgres. Postgres holds bookings, payments, refunds, customers, the hotel content cache and the audit log.
